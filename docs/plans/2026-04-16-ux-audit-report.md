## 2. 综合结论

### 2.1 总评

整体 UX 水平属于“有明确产品感和主题一致性，但局部交互闭环仍不够完整”的状态。

如果按 10 分制主观评分：

- 视觉一致性：`8.2/10`
- 信息密度控制：`6.7/10`
- 异常态与恢复能力：`5.8/10`
- 导航与可发现性：`6.6/10`
- 桌面中高密度数据场景适配：`7.4/10`
- 综合 UX：`7.0/10`

### 2.2 一句话判断

这个产品已经有了稳定的视觉骨架和较成熟的数据产品气质，但目前最明显的短板，不在“好不好看”，而在“出问题时用户能不能立刻看懂、能不能立刻恢复”。

## 4. 高优先级问题

### P1. 页面内没有把“失败原因 + 当前状态 + 恢复动作”讲清楚

这是本次最核心的问题。

运行态证据非常明确：

- 亚洲寡头页后台拉取 37 只股票时出现 `37/37 failed`
- 失败日志包含 `'NoneType' object is not subscriptable`
- 但页面仍主要呈现缓存数据与同步状态，没有把“本次刷新失败”明确告诉用户
- 外资大宗页超时后，页面截图 [tab-06.png](/D:/vcp_hunter/%E7%B4%AB%E9%87%91%E7%A0%94%E9%80%89/docs/ux_audit_assets/real/tab-06.png) 只显示“正在抓取大宗交易... 请稍候”的加载卡片，缺少失败提示、超时说明、重试按钮、缓存回退说明

这会导致用户产生两种危险误判：

- 误以为当前展示的是最新结果
- 误以为系统只是慢，而不是已经失败

这类问题对桌面行情/监控产品尤其严重，因为用户默认会把“界面还亮着”理解为“数据是可信的”。

建议优先改造为统一状态模型：

- `加载中`
- `已加载最新数据`
- `显示缓存数据`
- `本次刷新失败`
- `离线`

每个状态都必须同时给出：

- 状态标签
- 最后成功时间
- 失败原因摘要
- 重试动作

### P1. 多个页面的工具条仍然是单行横向堆叠，窄宽度下明显吃紧

这不是猜测，是真实缩窄截图已证实的问题。

证据：

- [earnings-1000.png](/D:/vcp_hunter/%E7%B4%AB%E9%87%91%E7%A0%94%E9%80%89/docs/ux_audit_assets/real-narrow/earnings-1000.png)
- [blocktrade-1000.png](/D:/vcp_hunter/%E7%B4%AB%E9%87%91%E7%A0%94%E9%80%89/docs/ux_audit_assets/real-narrow/blocktrade-1000.png)

表现：

- 控件间距被压缩
- 文本出现截断/拥挤
- 固定宽度控件一多，页面没有结构缓冲空间
- 业绩异动页是当前最明显的受害者

这说明当前工具条结构更像“为理想宽度排版”，而不是“为实际桌面窗口弹性排版”。

建议：

- 为通用工具条增加双行模式
- 把“筛选控件”和“动作按钮”分为上下两层
- 把次级条件收入弹出筛选面板
- 保留一个最窄宽度下的稳定布局基线

## 5. 中优先级问题

### P2. 顶部自定义标题栏目前能用，但扩展余量偏小

当前在真实桌面 1600 左右宽度下，顶部 9 个一级 Tab 还能维持基本稳定；这意味着它“现在没崩”。

但问题在于，它的扩展余量很小：

- 一级导航数量已经偏多
- 标题栏还要同时承担窗口控制、品牌识别、系统按钮等职责
- 一旦未来再加功能、加状态、加全局搜索，顶部会迅速进入拥堵区

所以这更像一个“可扩展性风险”，而不是“当前已不可用”。

建议：

- 维持当前结构不急着大改
- 但要提前准备“更多入口下沉”方案
- 后续新增一级功能时，优先进入二级菜单、工作区选择器或更多面板，而不是继续堆标题栏

### P2. 搜索/筛选反馈风格不统一

部分页面已经有较好的筛选反馈逻辑，但并不是全局一致。

风险在于：

- 用户改了筛选条件，不一定能快速确认“当前正在看哪一组数据”
- 一些页的筛选是输入即作用，一些页是按钮触发，一些页缺少明显清空反馈

建议统一成一套模式：

- 当前筛选摘要条
- 一键清空
- 数据总数/匹配数
- 更新时间
- 失败/缓存说明

日志页的交互反馈可以作为比较好的参考方向。

### P2. 自定义窗口按钮和部分核心操作按钮可发现性不足

当前最典型的点有两个：

- 顶部最小化、最大化、关闭按钮主要依赖图形直觉
- K 线窗口顶部关闭按钮也是图标化处理

问题不在于“用户看不懂 X”，而在于：

- 新用户没有额外语义提示
- 无障碍命名和 tooltip 不完整
- 高密度桌面场景下，图形按钮更容易被快速扫描忽略

建议：

- 给全部窗口控制按钮补 `tooltip`
- 给关键图标按钮补 `accessibleName`
- 对危险操作保留更清晰的悬停态

### P2. 亚洲寡头页把技术实现细节暴露给了业务用户

当前文案里直接出现了类似 `CF隧道`、直连通道、VPN/全局模式等技术术语。  
这对开发者是清楚的，但对普通业务用户不友好。

用户真正关心的是：

- 能不能连上
- 当前通道是否稳定
- 是否建议切换

而不是底层具体叫什么。

建议改成用户语言，例如：

- `高速通道`
- `备用通道`
- `当前连接不稳定，建议切换`

把技术术语放进二级说明或诊断详情，而不是主要操作文案。

### P2. Toast 的语义层级还不够强

当前 Toast 组件能工作，但在“成功 / 警告 / 错误 / 信息”之间的区分度还不够强。

已知代码层问题包括：

- `warning` 缺少足够醒目的图标语义
- 部分颜色语义存在定义但表达不完整

对于这类高频数据型桌面应用，Toast 不只是“告诉用户有消息”，还应该快速回答：

- 这是成功还是失败
- 严重程度多高
- 是否需要立即动作

### P2. Tooltip 溢出判断存在回归信号

测试已明确指出一个 UX 细节问题：

- `tests/test_theme_tokens.py::test_vcp_table_view_tooltip_only_shows_when_text_is_elided`

这意味着表格 tooltip 的触发条件可能不够准确，容易出现“不该弹的时候也弹”。  
这种问题单独看很小，但在高频表格产品里会明显影响浏览流畅度。

## 6. 分模块简评

### 6.1 关注池

优点：

- 结构最均衡之一
- 状态摘要区有效
- 表格信息密度可接受

问题：

- 右上行动区继续加按钮的话会很危险
- 缩窄后可扩展余量一般

### 6.2 龙虎榜 / 美股日报 / 盘中监控

这几页从整体框架看，主要问题不是视觉风格失控，而是通用工具条模式复用带来的密度风险。  
建议后续按“统一工具条改造”一起收敛，不要一页一页单修。

### 6.3 亚洲寡头

优点：

- 表格与状态色做得不错
- 缓存显示能力说明系统考虑过弱网络场景

问题：

- 本次刷新失败没有页面内讲清楚
- 技术术语过于靠前
- 用户看见数据，不一定知道这是不是最新数据

### 6.4 外资大宗

这是本次运行态里 UX 风险最高的页面之一。

从 [tab-06.png](/D:/vcp_hunter/%E7%B4%AB%E9%87%91%E7%A0%94%E9%80%89/docs/ux_audit_assets/real/tab-06.png) 看，页面在失败/超时场景下过于被动，只有加载卡片，没有恢复闭环。  
这会直接损伤用户信任。

### 6.5 业绩异动

这是本次窄宽度下布局压力最大的页面。  
从 [earnings-1000.png](/D:/vcp_hunter/%E7%B4%AB%E9%87%91%E7%A0%94%E9%80%89/docs/ux_audit_assets/real-narrow/earnings-1000.png) 看，筛选控件压缩已经很明显。

### 6.6 VCP 扫描

当前最佳页面。  
建议后续把它提炼成通用模板，反向指导其他数据页的：

- 页头层级
- 状态标签
- 行动按钮组织
- 表格状态表达

### 6.7 系统日志

日志页本身没有明显 UX 硬伤，但它承担了过多“解释系统问题”的责任。  
更理想的状态是：用户先在当前业务页就能理解问题，日志页只负责深层排障。

## 7. 优先整改路线图

### 第一阶段：1 到 3 天

目标：先补齐最影响信任的状态表达。

建议动作：

- 给外资大宗、亚洲寡头补页面内失败态和重试按钮
- 页面内明确显示“当前展示的是最新数据还是缓存数据”
- 给关键图标按钮补 tooltip 和 accessibleName
- 调整亚洲页用户文案，弱化技术术语

### 第二阶段：1 到 2 周

目标：把工具条从“能摆下”升级到“有弹性”。

建议动作：

- 建立通用双行工具条模式
- 固定宽度控件改为更弹性的布局策略
- 建立统一筛选摘要条
- 统一清空、刷新、失败提示、更新时间的位置

### 第三阶段：2 到 4 周

目标：形成可持续扩展的桌面交互骨架。

建议动作：

- 对顶部标题栏做一次容量治理
- 为后续新增一级功能准备下沉方案
- 提炼 VCP 扫描页为通用页面模板
- 统一状态容器、空态、离线态、缓存态、失败态组件

## 8. 本次审计的限制

### 8.1 K 线窗口未拿到最终运行态截图

K 线窗口相关代码已审查，但由于 `QtWebEngine` 初始化链路问题，本次没有拿到稳定的最终运行态截图。  
因此，K 线窗口的结论目前仍以代码层和结构层审计为主。

### 8.2 早期离屏截图不作为最终证据

本次前半段曾用离屏模式截图，但离屏环境分辨率只有 `800x800`，会误导真实布局判断。  
因此最终结论只以真实桌面截图目录 `real` 与 `real-narrow` 为主。

## 9. 最终判断

这次复核后，可以明确下结论：

- 产品不是“界面做得差”，而是“状态闭环还没做透”
- 当前最该补的不是美化，而是失败可见性、缓存透明度、重试路径
- 当前最值得保留和扩散的是 VCP 扫描页那套较成熟的页面组织方式

如果只让我给一个最核心建议，那就是：

**先把“数据失败时用户到底看到了什么、理解了什么、能做什么”补齐，再做下一轮视觉优化。**
