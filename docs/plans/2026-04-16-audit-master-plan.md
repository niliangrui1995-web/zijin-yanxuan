# 紫金研选全面审计与升级总方案

> **For Codex:** 本文档用于指导后续整仓审计与分阶段升级，不代表最终审计结论；后续所有发现、整改项、验证结果都应回挂到本方案对应章节，方便对账。

**Goal:** 对 `紫金研选` 项目进行一次覆盖架构、代码质量、UI/UX、运行稳定性、运行效率、功能一致性、数据刷新逻辑、缓存策略与测试治理的全量审计，并输出可执行的整改路线图。

**Architecture:** 项目当前是一个 Windows 优先的 `Python + PyQt6` 桌面终端，核心由 `vcp` 数据/策略层、`core` 基础设施层、`ui` 表现层、`earnings` 业绩子域组成；系统通过 `event_bus + global_store + task_manager` 组织跨模块协作，并依赖本地通达信数据、东方财富/新浪/AkShare/yfinance 等外部数据源。后续审计将沿“结构边界、运行链路、状态刷新、呈现一致性、工程护栏”五条主线推进。

**Tech Stack:** Python 3.10+, PyQt6, pandas, polars, numpy, AkShare, yfinance, pytest, ruff, PowerShell, Git

现有失败测试说明：项目已经存在“功能统一性”和“数据兜底逻辑”层面的可复现问题，不是纯风格债务。

1. `tests/test_asian_market_tab.py::test_asian_market_placeholder_rows_fill_track_for_missing_cache`
   现象：亚洲市场缺缓存占位行时，`2330.TW` 的 `赛道` 仍回落为 `未知赛道`。

   现象：亚洲 K 线回退到单票抓取时没有成功渲染数据帧。
   意义：K 线 fallback 链路与异步任务/视图刷新之间存在脱节。

### 2.5 当前高风险结构判断

基于静态扫描，当前最需要重点怀疑的结构风险如下：

- `MainWindowQT` 同时承担窗口外壳、状态栏、联网切换、主题切换、F5 流程、K 线打开、工作区装配与运行编排，控制器职责偏重。
- `TdxDataProvider` 同时承担本地数据、实时行情、外部 HTTP、熔断/冷却、缓存清理、批量抓取、K 线拼装，职责边界过宽。
- `CentralQuotesService + global_store + event_bus` 形成了隐式全局状态链路，需要重点核查刷新顺序、重复广播和关闭期竞态。
- `BaseStockTab` 累积了大量跨 Tab 公共逻辑，但也夹杂了外部程序拉起、复制、缓存刷新、市值刷新等多种责任，继续膨胀会降低可维护性。
- `core/market_calendar.py` 已经具备“状态机”雏形，但其复杂度较高，必须验证交易日/午休/盘后/跨市场判定是否与真实刷新策略严格一致。

## 3. 审计目标与总原则

本次审计不是只找代码风格问题，而是要回答以下核心问题：

1. 这个项目的系统结构是否还能继续演进，还是已经进入“改一处伤三处”的脆弱态。
2. 运行时最容易出故障的链路是什么，是否存在关闭期、切网期、刷新期的竞态或脏状态。
3. 数据在不同时间与不同页面上的展示是否一致，尤其是 `现价/涨幅/市值/赛道/买点/K线` 这些核心业务字段。
4. 缓存与刷新机制是否合理，是否存在过期不失效、重复刷、午休误判、盘后误拉、F5 后快照不一致等问题。
5. UI/UX 是否清晰、统一、反馈充分，是否存在“功能有了但用户不理解当前状态”的问题。
6. 当前代码是否具备后续继续修复和扩展的可维护性基础。

审计总原则：

- 先建立事实基线，再给整改建议。
- 优先抓真实 bug、真实脆弱点、真实一致性问题，不做空泛点评。
- 所有结论必须能落到文件、模块、场景或测试案例。
- 审计报告和整改计划必须可对账、可追踪、可回归验证。

## 5. 审计结果输出标准

后续正式审计输出统一按以下格式落地，方便对账：

1. `总报告`
   一个总览文档，汇总所有域的分数、阻断项和升级优先级。

2. `分域报告`
   每个审计维度单独成节，记录：
   - 问题编号
   - 严重度
   - 文件位置
   - 复现条件
   - 影响范围
   - 建议动作

3. `整改台账`
   建议用 Markdown 表格或 CSV，字段至少包括：
   - `ID`
   - `Domain`
   - `Severity`
   - `File`
   - `Symptom`
   - `Root Cause`
   - `Fix Proposal`
   - `Owner`
   - `Status`

4. `回归验证清单`
   每个修复项必须绑定测试、日志或手工验收步骤。

## 6. 审计评分模型

建议把后续正式审计评分统一为 100 分：

| 维度 | 权重 |
| --- | ---: |
| 架构与边界 | 15 |
| 代码整洁性与可维护性 | 15 |
| 稳定性与生命周期 | 20 |
| 性能与效率 | 15 |
| 数据刷新与缓存正确性 | 20 |
| UI / UX 与交互一致性 | 10 |
| 测试与工程护栏 | 5 |

评分解释：

- `90-100`：整体成熟，仅需小修
- `75-89`：可持续维护，但有明显债务
- `60-74`：可运行但高风险，必须分期整改
- `40-59`：脆弱，已影响迭代效率
- `<40`：需要先止血再谈扩展

## 7. 三种审计模式

为了适配不同目标，后续正式审计可按三种模式执行。

### 模式 A：稳定性优先

适用场景：近期要继续使用、需要先止血。

优先顺序：

1. 失败测试与真实 bug
2. 生命周期与任务取消
3. 数据刷新/缓存正确性
4. 关键页面 UI 状态反馈
5. 其余结构债务

### 模式 B：架构治理优先

适用场景：准备持续迭代、要降低后续改动成本。

优先顺序：

1. 模块边界与职责拆分
2. 大文件治理
3. 隐式全局状态治理
4. 测试护栏
5. 性能与 UX

### 模式 C：体验与效率优先

适用场景：用户层面已明显感知卡顿、乱、反馈不足。

优先顺序：

1. 冷启动与盘中刷新性能
2. 表格渲染/状态提示/占位逻辑
3. K 线交互一致性
4. 缓存命中与去重策略
5. 架构拆分

**建议默认采用：模式 A + 模式 B 的组合**

原因：当前仓库已经有 2 个真实失败测试和较大的 lint/结构债务，必须先保稳定，再控耦合。

## 8. 分阶段升级路线

## Phase 2：数据刷新与缓存治理

## Phase 3：架构降耦与大文件拆分

**目标**

- 降低后续维护成本，把“能跑但不敢动”的文件拆开。

**优先对象**

**退出条件**

## Phase 4：UI / UX 统一与性能优化

**目标**

**退出条件**

**退出条件**

## 9. 后续正式审计的执行顺序建议

建议按以下顺序开展正式审计：

1. `基线报告`
2. `稳定性/刷新链路审计`
3. `功能一致性审计`
4. `架构边界审计`
5. `性能审计`
6. `UI/UX 审计`
7. `测试与工程护栏审计`
8. `总报告 + 整改路线图 + 回归清单`

原因：

- 当前仓库已经出现真实失败测试，先做稳定性与数据正确性，收益最高。
- 架构问题很重，但如果不先厘清刷新链路和功能语义，拆分容易把 bug 带着一起扩散。
- UI/UX 优化应建立在语义一致、状态清晰、数据可信的基础上。

## 10. 审计阶段的对账方式

建议后续所有正式审计结果都采用以下编号：

- `ARCH-xxx`：架构
- `CLEAN-xxx`：代码整洁性
- `STAB-xxx`：稳定性
- `PERF-xxx`：性能
- `DATA-xxx`：刷新与缓存
- `UX-xxx`：UI/UX
- `FUNC-xxx`：功能一致性
- `QA-xxx`：测试与工程护栏

示例：

- `DATA-003`：午休状态下报价刷新策略与 UI 文案不一致
- `STAB-002`：窗口关闭后后台任务回调仍可能命中已销毁对象
- `FUNC-001`：亚洲市场占位数据赛道字段与真实业务语义不一致

## 11. 当前结论

基于当前静态扫描和基线执行结果，可以先下三个阶段性判断：

1. **项目不是“不可用”，但已经进入“结构复杂、局部脆弱、继续堆功能会加速失控”的阶段。**
2. **短期最值得优先投入的，不是大面积重写，而是先抓稳定性、刷新正确性和功能语义统一。**
3. **中期必须控制 `MainWindowQT / TdxDataProvider / table_models / KLineWindow / MarketCalendar` 这几处大文件，否则后续每次修复都会带来额外回归风险。**
