# 紫金研选项目审计报告

> 对应总方案：`docs/plans/2026-04-16-audit-master-plan.md`
>
> 说明：本报告按总方案既定维度执行，先看代码与测试证据，再给结论和建议；尽量用非技术语言描述，方便后续对账。

## 1. 审计结论

**一句话结论：**

这个项目**不是“不能用”**，而是已经进入了“功能越来越多、结构开始吃力”的阶段。它现在还能跑，且有一些不错的基础，但如果继续在现有结构上叠功能，后面会越来越难修、越来越难查问题。

**当前总体判断：**

- 可用性：`中上`
- 稳定性：`中`
- 可维护性：`中下`
- UI/UX 基础：`中上`
- 工程护栏：`中下`

**本次已核对的事实基线：**

- `pytest -q`：`180 passed, 2 failed`
- `ruff check .`：`595` 个问题
- 最大热点文件集中在：
  - `vcp/data_provider.py`
  - `ui/models/table_models.py`
  - `ui/kline_window_qt.py`
  - `ui/main_window_qt.py`
  - `core/market_calendar.py`

## 2. 项目优点

先说优点，避免报告只剩“批评”：

1. **有离线优先思路**
   项目启动时优先保证本地可用，再异步补联网数据，这个方向是对的。

2. **主题与视觉 token 体系已经成型**
   `ui/theme.py`、`ui/theme_tokens.py`、`ui/components/main_window_shell.py` 说明 UI 不是纯堆砌，已经有统一视觉基础。

3. **测试不是空白**
   重点链路已经有回归测试，例如：
   - `tests/test_data_provider_realtime_failover.py`
   - `tests/test_central_quotes_worker.py`
   - `tests/test_market_calendar_exchange_sessions.py`
   - `tests/test_theme_tokens.py`

4. **缓存、启动、中央报价这些核心能力已经被抽出来了**
   说明项目不是“完全散装”，只是目前边界还不够干净。

## 3. 主要问题

下面是本次审计确认的问题，按优先级从高到低写。

### 高优先级 1：实时数据刷新不是单一入口，后期很容易出现“同一份数据多处乱发”

**看懂版：**

现在“实时行情更新”这件事，不是一个地方统一发，而是多个地方都能发。短期看是方便，长期看最容易出现“有的页面更新了、有的页面慢一拍、调试时不知道是谁发的”。

**证据：**

- `ui/workers/central_quotes_worker.py:274`
- `ui/workers/central_quotes_worker.py:366`
- `ui/tabs/base_stock_tab.py:160`
- `ui/tabs/base_stock_tab.py:714`
- `core/global_store.py:22`

**影响：**

- 同一个总线信号 `sig_rt_quotes` 有多个生产者。
- `global_store` 又在后台默默吃这个信号并写全局状态。
- 一旦出现行情错位、晚到、覆盖、重复刷新，定位成本会很高。

**优化建议：**

- 只保留一个“实时行情广播主入口”，建议就是 `CentralQuotesService`。
- `BaseStockTab` 不再直接广播行情，只返回数据给中央服务合并。
- 给 `sig_rt_quotes` 制定统一 payload 规范，禁止半成品数据直接上总线。

### 高优先级 2：事件语义开始混用，`cache_loaded` 已经不只是“缓存加载完成”

**看懂版：**

有些信号名字看起来很清楚，但实际上已经被拿去做别的事了。这样写久了以后，代码会越来越像“暗号系统”，新问题会越来越难查。

**证据：**

- `ui/startup_loader.py:123` 启动时发 `sig_cache_loaded`
- `ui/main_window_qt.py:616` F5 后发 `sig_cache_loaded`
- `ui/tabs/lhb_tab.py:256` 龙虎榜更新后也发 `sig_cache_loaded`
- `ui/tabs/watchlist_tab.py:43` 监听这个信号做自己的刷新

**影响：**

- “缓存加载完成”和“某个业务 Tab 数据更新完成”被混成一件事。
- 会导致页面被额外刷新，或者后续开发者误判触发时机。

**优化建议：**

- 把 `sig_cache_loaded` 收回成“只表示缓存初始化完成”。
- 龙虎榜、业绩、大宗等各自用独立业务信号。
- 每个全局信号都写清楚“谁发、什么时候发、谁能监听”。

### 高优先级 3：几个核心类太重，已经接近“巨石文件”

**看懂版：**

现在最核心的几个文件，已经不是“一个文件负责一件事”，而是“一个文件管很多事”。这类代码前期开发快，后期维护很痛苦。

**证据：**

- `vcp/data_provider.py`：`1405` 行
- `ui/models/table_models.py`：`1241` 行
- `ui/kline_window_qt.py`：`1140` 行
- `ui/main_window_qt.py`：`727` 行
- `core/market_calendar.py`：`712` 行

**典型症状：**

- `MainWindowQT` 既管主窗口、又管 F5、又管联网、又管工作区装配、又管关闭流程。
- `TdxDataProvider` 同时管本地数据、联网报价、冷却机制、缓存整理、网络探测。
- `KLineChartWindow` 同时管 UI、数据读取、亚洲回退拉取、实时更新。

**影响：**

- 修一个点，容易误伤别的点。
- 测试必须绕过一大堆无关逻辑，越来越难写。
- 新人很难快速接手。

**优化建议：**

- `MainWindowQT` 拆成：窗口壳、启动编排、行情编排、关闭编排。
- `TdxDataProvider` 拆成：本地数据层、实时行情层、网络/冷却策略层。
- `KLineChartWindow` 拆成：K 线数据加载器、K 线渲染器、窗口交互层。

### 高优先级 4：已经存在两个真实功能 bug，不是“纸面风险”

**看懂版：**

当前项目里已经有能复现的真实问题，而不是只有风格或结构问题。

**证据：**

- `tests/test_asian_market_tab.py::test_asian_market_placeholder_rows_fill_track_for_missing_cache`
- `tests/test_kline_window_header.py::test_kline_load_asian_chart_falls_back_to_single_ticket_fetch`

**问题 1：亚洲市场缺缓存时，占位数据的“赛道”不统一**

- `vcp/fetchers/asian_kline_fetcher.py:114`
- `vcp/fetchers/asian_kline_fetcher.py:124`
- `ui/tabs/asian_market_tab.py:500`
- `ui/tabs/asian_market_tab.py:530`

现象：`2330.TW` 缺缓存时，页面里会出现“未知赛道”。

**问题 2：亚洲 K 线单票回退链路不稳**

- `ui/kline_window_qt.py:810`
- `ui/kline_window_qt.py:866`

现象：本地没有 K 线缓存时，理论上应该单独回源拉取，但当前测试失败说明这条回退链路不可靠。

**我对根因的判断：**

第二个问题大概率与 `KLineWindow` 在函数内部直接 `from ... import fetch_single_kline` 有关。这样会让测试替身和后续替换逻辑都变脆，回退链路可测性也变差。

**优化建议：**

- 亚洲赛道映射补全，不要把核心标的落到“未知赛道”。
- `fetch_single_kline` 改成模块依赖注入或统一从模块对象读取，不要在局部函数里直接绑定。

### 高优先级 5：吞异常过多，很多问题会“失败了但不明显”

**看懂版：**

项目里有很多 `except Exception`。这类写法在临时救火时有用，但太多以后，真正的 bug 会被“压下去”，用户只看到“不更新”或者“偶尔失效”。

**量化结果：**

- 全仓宽兜底异常：约 `240` 处
- 最高文件分布：
  - `vcp/data_provider.py`：`29`
  - `ui/main_window_qt.py`：`17`
  - `ui/tabs/base_stock_tab.py`：`16`
  - `ui/kline_window_qt.py`：`15`

**影响：**

- 出错时常常只写一条日志，或者直接静默跳过。
- 用户感知是“没反应”，开发者感知是“复现困难”。

**优化建议：**

- 对核心链路分级处理异常：网络异常、空数据异常、编程错误要分开。
- UI 可恢复错误可以提示用户；编程错误不要直接吞。
- 先从 `data_provider.py`、`main_window_qt.py`、`kline_window_qt.py` 这三个文件开始治理。

### 中优先级 6：全局状态耦合偏重，生命周期容易出现隐藏副作用

**看懂版：**

有一些状态不是“明确传进来”，而是全局对象自己订阅、自己更新。这样写短期省事，长期最容易出现“谁改了状态我都不知道”的问题。

**证据：**

- `core/global_store.py:22`
- `ui/workers/central_quotes_worker.py` 直接读取 `main_window.tab_scan / tab_rt / tab_watchlist / tab_lhb / tab_earnings` 等
- `ui/main_window_qt.py:445-459` 把工作区里的 Tab 再挂到主窗口属性上

**影响：**

- 工作区、主窗口、中央报价器之间互相知道太多。
- 关闭窗口、切换工作区、后续加第二种 workspace 时，风险会明显增大。

**优化建议：**

- 用“注册活跃代码来源”的方式替代 `CentralQuotesService` 直接摸所有 Tab。
- `global_store` 增加明确的生命周期管理，不要只在 import 时绑定一次。

### 中优先级 7：缓存与定时器链路复杂，已经出现重复初始化痕迹

**看懂版：**

缓存、自动刷新、盘后静默同步这些机制本身是必要的，但目前链路有点绕，局部还出现了重复代码，说明这里已经不够稳了。

**证据：**

- `ui/tabs/asian_market_tab.py:84`
- `ui/tabs/asian_market_tab.py:85`

这里同一个 `auto_cache_timer` 被连续初始化了两次。

**影响：**

- 当前不一定立刻炸，但说明这个模块经历过多轮叠加修改。
- 后续继续加逻辑时，很容易引入定时器重复绑定、状态错位、关闭不干净。

**优化建议：**

- 统一梳理亚洲市场模块的“分钟轮询 / 盘后同步 / 手动刷新 / 静默等待”状态机。
- 每个状态只保留一个定时器和一个职责。

### 中优先级 8：已经出现编码乱码，后续维护风险很高

**看懂版：**

仓库里已经出现了真实乱码，不是理论风险。

**证据：**

- `ui/main_window_qt.py:614`
- `ui/main_window_qt.py:618`

这两条日志文本已经是乱码。

**影响：**

- 排错日志不可读。
- 后续改代码时最容易把文件继续改坏。
- 对中文项目尤其危险。

**优化建议：**

- 全仓统一 UTF-8。
- 在提交前增加编码检查。
- 先把现有乱码点修掉，再禁止编辑器自动混入其他编码。

### 中优先级 9：UI 基础不错，但“状态表达”还没有真正统一

**看懂版：**

这个项目的视觉基础不差，但“用户现在看到的数据是实时、缓存、静默还是回退”的表达还不够统一。

**证据：**

- 有主题和 token 体系：`ui/theme.py`、`ui/theme_tokens.py`
- 有状态栏组件：`ui/components/main_window_shell.py`
- 各 Tab 也普遍有自己的状态文本

**问题在于：**

- 状态表达主要靠文字日志和局部标签，统一性不够。
- 不同页面对“实时中 / 缓存中 / 静默中 / 错误 / 可手动刷新”的说法不完全一致。

**影响：**

- 用户知道“页面变了”，但不一定知道“为什么变、当前是不是最新”。
- 出现网络或缓存问题时，非技术用户会更迷糊。

**优化建议：**

- 给全局和每个 Tab 统一一套状态词典：
  - `实时`
  - `缓存`
  - `静默`
  - `回退`
  - `错误`
- 尽量用固定 badge/颜色，不只靠一长串文字。

### 中优先级 10：工程规则有了，但自动门禁还没补齐

**看懂版：**

项目不是没有规范，但规范目前主要靠“本机自觉执行”，不是“仓库自动拦截”。

**证据：**

- 有 `ruff` 配置：`pyproject.toml`
- 有 `pre-commit`：`.pre-commit-config.yaml`
- 但没有 `.github/workflows`
- 当前 `ruff check .` 还有 `595` 个问题

**影响：**

- 每个人本地环境不同，质量结果可能不一致。
- 规则不能自动挡住坏提交。

**优化建议：**

- 先做一次 lint 基线清理。
- 增加最小 CI：
  - `pytest -q`
  - `ruff check .`
- 没必要一步到位上复杂流水线，先把最小门禁立住。

## 5. 优先整改顺序

如果只按投入产出比排序，我建议这样做：

### 第一阶段：先修真实 bug 和信号乱用

1. 修复亚洲占位行“赛道”不统一问题
2. 修复亚洲 K 线单票回退问题
3. 收敛 `sig_rt_quotes` 生产者
4. 收敛 `sig_cache_loaded` 语义

### 第二阶段：拆最重的三个模块

1. 拆 `vcp/data_provider.py`
2. 拆 `ui/kline_window_qt.py`
3. 拆 `ui/main_window_qt.py`

### 第三阶段：补工程门禁

1. 清理 `ruff` 问题到可接受基线
2. 建最小 CI
3. 加编码检查，防止再出乱码

## 6. 我对后续优化的建议

如果你问我“下一步最值得做什么”，我的建议很简单：

- **不要马上全仓大重构**
  先修真实 bug，再收敛信号和状态入口。

- **不要继续往巨型文件里加新功能**
  先把最重的几个文件切开，再加功能。

- **先统一数据刷新入口，再谈性能**
  现在最大的效率风险，不一定是算法慢，而是“同一件事做了多次”。

- **把“用户看到的数据状态”表达清楚**
  这会立刻提升产品可理解性，也会减少你后面排查“是不是没刷新”的沟通成本。

## 7. 本次审计边界说明

本次报告已经覆盖：

- 架构与边界
- 代码整洁性
- 稳定性与生命周期
- 刷新逻辑与缓存机制
- UI/UX 结构
- 测试与工程护栏

本次**没有**做的内容：

- 长时间真实盘中压测
- 人工完整交互走查
- 真机性能 profiler 报告

所以本报告里的“性能”判断，当前主要基于代码结构和刷新链路，不是基于长时间运行数据。

---

**最终结论：**

这个项目值得继续做，但现在最该做的不是再加功能，而是先把“刷新链路、事件语义、巨型文件、异常处理”这四个地方收紧。只要这四个点收住，后面的稳定性、性能、可维护性都会明显提升。
